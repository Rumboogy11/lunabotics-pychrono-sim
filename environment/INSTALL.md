# Installation

`./install.sh` turns a fresh Arch Linux, CachyOS, Debian, or Ubuntu host into a
working checkout of this project. It installs system prerequisites, creates a
project-local `chrono-env`, checks out the custom Chrono 11 fork, and builds/installs
PyChrono with FSI-SPH, vehicle, robot-model, and PardisoMKL modules. Nothing is
installed into the system Python.

## Quick install

```bash
git clone https://github.com/Rumboogy11/lunabotics-pychrono-sim.git
cd lunabotics-pychrono-sim
./install.sh
```

If you do not have root/sudo access, install the few system packages yourself
and run:

```bash
./install.sh --no-system-packages
```

Common options:

| Option | Purpose |
| --- | --- |
| `--no-system-packages` | Skip `pacman`/`apt`; use tools already on `PATH` |
| `--without-paraview` | Skip the system ParaView GUI (installed by default) |
| `--with-paraview` | Force the default system ParaView install |
| `--cuda-arch NNN` | Override GPU arch (e.g. `86`, `89`, `120`); auto-detected otherwise |
| `--jobs N` | Request parallel build jobs (default/ceiling: `nproc - 2`, minimum 1) |
| `--clean` | Remove `chrono-build/` and `chrono-install/` before rebuilding |
| `--skip-build` | Install env/source/deps only, do not compile Chrono |
| `--skip-patch` | Do not apply the local SPH and Python stress patches to the Chrono checkout |
| `--chrono-repo URL` / `--chrono-ref REF` | Override the custom fork URL/commit |
| `--work-root PATH` | Store env/build/source outside the checkout (useful on NTFS/FUSE mounts) |

The install is idempotent: re-running it updates the environment and rebuilds
only what is needed. Source changes are preserved; `--clean` only removes the
build and install trees.

## What gets installed

| Path | Purpose |
| --- | --- |
| `chrono-src/` | Custom Chrono 11 checkout pinned to commit `757a75b3c3…` from `https://github.com/Rumboogy11/chrono.git`, plus `environment/patches/chrono-local-crm-sph.patch` (BVH-accelerated BCE generation) and `environment/patches/chrono-python-von-mises.patch` (native von Mises stress in Python) |
| `chrono-env/` | Project-local conda-forge env: Python 3.12, CMake 3.31, Ninja, SWIG 4.5.1, GCC 13.4, CUDA 12.9, Eigen, yaml-cpp, oneMKL 2025.2, Tk, X11/GL runtime libs, NumPy, Matplotlib, PyVista/VTK, trimesh, tetgen, pymeshfix, OCP |
| `chrono-build/` | CMake/Ninja build tree |
| `chrono-install/` | Installed Chrono libraries and `pychrono` Python modules |
| `.tools/` | Downloaded micromamba binary |
| `.mamba/` | Downloaded conda packages cache |

No CAD or mesh geometry is shipped or generated by the installer. Supply your own
files in the gitignored `geometry/` directory, or convert a STEP model with the
study wizard.

If the checkout is on NTFS, exFAT, FUSE, CIFS, or another filesystem that
cannot host conda's symlinks, the installer automatically places all six
directories under `${XDG_DATA_HOME:-$HOME/.local/share}/pychrono/<hash>/` and
creates symlinks in the project root. Set `PYCHRONO_WORK_ROOT` or pass
`--work-root PATH` to choose that location yourself.

The project pins conda-forge GCC 13.4 because GCC 14.4 has several internal
compiler errors in this Chrono revision, including at `-O2`. The C++ release
build uses `-O2`; set `CHRONO_CXX_RELEASE_FLAGS='-O3 -DNDEBUG'` only if you
change the toolchain to one that has been tested with that setting.

Chrono's Eigen-heavy sources need several GB of memory per compiler process and
can trigger GCC front-end crashes when compiled too aggressively. The installer
uses all but two of the machine's available threads for the Chrono build (at
least one), while the activated environment still defaults `OMP_NUM_THREADS` to
half of the available threads. Use `--jobs 1` for the most conservative build.
An explicit `OMP_NUM_THREADS` is never overridden. The build-job cap applies only
to the Chrono build; the build script raises the compiler stack limit and retries
remaining objects serially after a front-end crash.

Thread detection ignores `OMP_NUM_THREADS`, so re-running the installer from an
already activated shell still selects all but two of the machine's real CPUs for
the build. If a parallel compile is interrupted by a GCC internal compiler error,
the build script retries the remaining objects serially; genuine source errors
still fail. The build script also raises the compiler's soft stack limit because
Eigen-heavy Chrono sources can otherwise crash `cc1plus` with a segmentation
fault.

The PyPI/conda-forge `pychrono` package is deliberately **not** used: it lacks
`pychrono.fsi`/`pychrono.vehicle` and the local PardisoMKL binding, and its
shared libraries conflict with the source build. All launchers now keep the
one-way replay on the same local Chrono 11 bindings as rigid CRM. The installer
removes an old conda `pychrono` package if it finds one in `chrono-env`.

### CUDA notes

- The custom FSI-SPH source requires **CUDA 12.9** (CUDA 13 is not supported).
- A compatible NVIDIA driver must be present at runtime; `nvcc` and the CUDA
  libraries are installed inside `chrono-env`, so a system CUDA toolkit is not
  required.
- The installer queries `nvidia-smi` for the first GPU's compute capability and
  stores it in `chrono-env/etc/chrono-cuda-arch`. Automatic detection fails on
  machines without `nvidia-smi`; pass `--cuda-arch NNN` there.
- The original workstation used `sm_120` (RTX 5070 Ti).

## Activate and verify

```bash
source environment/activate-chrono-source.sh

"$CHRONO_ENV/bin/python" - <<'PY'
import pychrono.core, pychrono.fea, pychrono.fsi, pychrono.pardisomkl, pychrono.vehicle
print("CRM/full Python modules available")
PY

PYTHON="$CHRONO_ENV/bin/python" ./crm/run.sh --smoke-test --mesh-file /path/to/your_drum.obj
```

Replace `/path/to/your_drum.obj` with a local CRM surface mesh; no reference
geometry is bundled with the installer.

Runners select `chrono-env/bin/python` automatically when `PYTHON` is unset and
the local environment is present.

`./crm/run.sh --help` and `./crm/run.sh --print-soil` work without CRM modules
because Chrono imports are deferred until a simulation starts.

## System packages

The installer uses `pacman` on Arch/CachyOS and `apt-get` on Debian/Ubuntu to
install: `git`, `curl`, `bzip2`, `tar`, coreutils/awk/sed, `python3`, Tk support,
`xdg-utils`, Xvfb, X11/GL/Qt xcb runtime libraries needed by VTK, PyVista, OCP,
and the Tk GUI, plus the full ParaView GUI and Python bindings (`paraview`/
`pvpython`; Debian/Ubuntu also installs `python3-paraview`). When not
already running as root, those package commands are invoked through `sudo`
(prompting for a password if needed). No other installer command is elevated:
pip/conda packages, downloads, git operations, and the Chrono build run as the
invoking user. Use `--without-paraview` to skip the system ParaView package. With
`--no-system-packages`, ParaView, Xvfb, and the display server are not installed
and must already exist on the host.

On a headless host, run GUI tools through a virtual X server:

```bash
xvfb-run ./run_study_gui.sh
```

Launchers add `chrono-env/bin` to `PATH` automatically. The study GUI also
checks that its Python has Tkinter and falls back to `chrono-env/bin/python`
when the system Python does not.

## Optional tools

- `view_results.py` plots CRM/FEA summaries and writes `results_overview.png`.
- `view_geometry.py` compares STEP CAD vs converted mesh/surface.
- `export_study_vtk.py` exports studies for ParaView. `view_study_paraview.py`
  imports `paraview.simple` and PySide6 from ParaView's own Python, so run it
  with `pvpython view_study_paraview.py <export_dir>` or the full Qt GUI via
  `paraview --script=view_study_paraview.py`. Both commands come from the
  system ParaView package and are exposed by the project launchers.
- `stl_to_obj.py` converts STL meshes to OBJ (pure format conversion, no extra deps).
- `fast-simplification` is not required by the current tools.

## Notes

- Run commands from the project root unless a script states otherwise.
- Large outputs are written under `Output_*` (ignored by git). Prefer project-local paths over `/tmp`.
- See `README.md` and `crm/README.md` for workflows and options.
